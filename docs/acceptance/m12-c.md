# M12-C — 异常媒体恢复、错误信息脱敏与会话回归

## 基线与工作边界

本阶段基于 M12-B PR #27 的代码 SHA a8357f11c670205362ed44293eb85d3388aa51ab 开发。该 SHA 的 Windows M1/M2 CI 均通过，用户明确反馈 M12-B Windows 10/10 项全部实际验收通过（包括两轮长时间资源对照及合法受控弱网）。**此前 PR #20–#27 仍是 Draft，未获逐项合并授权。**

M12-C 是 M12 稳定性与安全加固的下一子阶段。重点检查文件损坏、非法容器、文件移动和旧会话回调，不修改 libmpv 核心解码器、不自动篡改 Windows 网络配置、不尝试绕过合法授权/DRM。测试数据均在独立的新目录内生成，不触碰原始电影、收藏和应用用户数据。

## 源码变更

- Rust player/engine.rs：原生错误原来可能把 libmpv 的 Display / Debug 文本返回给前端或记录到普通日志。现仅允许 Raw(有界整数) 形式的原生错误码通过；其他原生错误固定为 mpv_native_error，用户可见消息由程序给出，不包含来自媒体 URL、签名 query、文件名、路径或远端响应体的原始字符串。保留 libmpv Raw(-13) 的泛化排查提示，但绝不把 -13 直接解释为 HTTP 403。
- Rust 单元测试：拒绝携带签名 token、文件路径及不规范错误码的原生诊断字符串；播放状态机验证损坏媒体触发的 Error 不能被误转成自然 Ended，随后新建的健康会话不继承上个会话的错误。
- scripts/create-m12c-fault-fixtures.ps1：使用用户已知的 FFmpeg 可执行文件（默认 D:\26-008\26-008\voip4\run\run_windows\bin\ffmpeg.exe）在全新的 %TEMP% 独立目录创建 7 组数据：healthy.mp4、empty.mp4、random-bytes.mp4、html-disguised.mp4、truncated-header.mp4、truncated-tail.mp4、wrong-extension.txt。明确拒绝覆盖已有目录。
- scripts/verify-m12c-fixtures.mjs 和 scripts/m12c-fixture-policy.mjs：只读验证固定的七组文件的大小、基础结构、截断关系、manifest 和 SHA-256；拒绝任意相对路径/绝对路径、符号链接、超大输入，不修改样本或上传信息。
- tests/m12c-fault-fixtures.test.mjs：固定案例检查、数据完整性、越界/路径穿越/重复条目等失败路径。加入 npm run build 的 Windows M1/M2 检查链。

**重要解释**：truncated-tail.mp4 不一定解码失败，FFmpeg/MP4 的索引可能保留部分可播放内容；验收目标是无崩溃、不会错误跳集，绝不能强行要求此文件必须进入 Error。损坏文件引发真实错误时不能记成自然 EOF；关闭程序或手动 Stop 也不能当成自然 EOF。

## Windows 使用方法

所有下面命令在 GitHub 仓库根目录执行；不要将它们指向用户真实媒体目录。PowerShell 为 Windows 自带环境，Node.js 为项目现有开发依赖。

1. 生成七个独立媒体文件，命令：

~~~powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\create-m12c-fault-fixtures.ps1
~~~

脚本输出独立的临时目录路径（每次创建新随机目录），不会复用、清理或覆盖已有目录。请记下控制台打印出的目录。也可用 -OutputDirectory 指定一个**不存在的新目录**；现有目录会直接拒绝。

2. 确认场景文件完整，使用上述实际临时目录路径：

~~~powershell
node .\scripts\verify-m12c-fixtures.mjs --dir "这里填刚刚打印的隔离目录"
~~~

应看到 7 个 fixture 的 SHA-256 和大小及 PASS。若提示缺失、大小异常、无法解析、目录是符号链接等，先修复素材，不要继续在播放器中验收。

3. 在 M12-C 单独部署的 Windows 调试 EXE 上，手动从“打开本地 MP4”逐个选入生成文件；先用 healthy.mp4 验证音画与自然 EOF。测试损坏文件时建议先关闭本地自动连播，以免误把队列策略和真实播放器错误混淆。

4. 如果要测试“本地库文件被移动”，**只使用这些新生成的合成文件**：先将 healthy.mp4 导入应用本地媒体库、关掉相关占用，再在该测试目录中手工重命名或暂时移动此文件；从应用尝试打开该已导入条目。预期友好报错且不会启动无限重试，也不删除历史；测试后将它移回原处。绝不要重命名或移动个人影片。

5. 故意构造不存在或无效的公开 HTTPS MP4 地址时，先测试已经被拒绝的语法格式，不实际对非授权外部服务器制造流量：例如 http://example.com/video.mp4、https://localhost/video.mp4、https://user:password@example.com/video.mp4。后续真实受控弱网场景继续依照 M12-B 已验证方法进行，禁止上传原始带鉴权参数的日志。
