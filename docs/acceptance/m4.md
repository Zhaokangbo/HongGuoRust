# HongGuoRust M4 — buffering, state and reliability acceptance

Status: **IN DEVELOPMENT**. Not a claim of Windows playback PASS.

## Scope

M4 retains a single Rust-owned libmpv worker and adds a seventh externally visible state, `Buffering`. Native `paused-for-cache` observations are independent from the user's pause intent. The state reducer prioritizes **Paused** while the user has requested pause; after resume, it returns to **Buffering** if cache remains unavailable, otherwise **Playing** once the session has started. Buffering before the first restart is permitted. Late cache/restart events for old sessions and events after terminal Ended/Error must be ignored.

M4 does not use absence of video frames to infer cache starvation, does not label `FileLoaded` or `PlaybackRestart` as a true displayed first frame, and does not change media-provider access or authorization.

## HTTPS regression reported by Windows user — 2026-11-21

**Reported:** public HTTPS MP4 worked in the released M3 executable, but in an M4 test build clicking `播放 HTTPS` showed `媒体加载失败`. The original uploaded screenshot was not legible, so the exact URL, HTTP status and M4 player log have **not** yet been independently verified. This is an M4 regression candidate and blocks merge even if the existing local-file CI is green.

**Code review:** `source.rs` and the Rust `loadfile` / network initialization path are identical in M3 and M4. M4 added high-frequency synchronous cache-property reads before the first `FileLoaded` and mistakenly treated `EndFile(Redirect)` as an error. The follow-up code correction (1) only polls `paused-for-cache` after `FileLoaded`, at most once every 200ms, and (2) allows a native redirect event to continue without declaring terminal failure. These changes address identified defects but **do not yet prove the user's HTTP loading failure is fixed**.

**Next checks:** Re-run M4 Windows CI, compare the exact same URL and DLL SHA-256 between M3/M4, and obtain the failed session's `%LOCALAPPDATA%\\HongGuoRust\\logs\\player-<pid>.log` (remove any private URLs/tokens before sharing). Record whether the error is `Raw(-13)`, `unexpected_end_reason_*`, or a network-stage code. The M4 HTTPS gate stays FAIL / unverified until a real Windows test confirms an actual decoded frame and a working timeline. The hosted M1/M2 CI currently does not make an external HTTPS video request.

## Opt-in libmpv network diagnostic (after 2026-11-21 Raw(-13) report)

The reported public HTTPS session failed in ~14–18ms after `loadfile accepted`, without any `file-loaded` event; libmpv returned MPV_ERROR_LOADING_FAILED (-13). Its generic code does **not** distinguish HTTP 403, TLS/DNS, failed stream opening or other media loading conditions. The earlier native-event adjustments are candidate mitigations, **not an independently verified fix**.

A debug environment variable enables the native mpv log file for each session, while normal users generate no additional mpv logs:

```powershell
# In the directory that contains the freshly built hongguorust.exe and libmpv-2.dll:
$env:HONGGUORUST_MPV_DEBUG = "1"
.\hongguorust.exe
# Play the same public HTTPS MP4, then exit
Remove-Item Env:\HONGGUORUST_MPV_DEBUG
# Locate the latest per-session verbose mpv file:
Get-ChildItem "$env:LOCALAPPDATA\HongGuoRust\logs" -Filter "mpv-*.log" |
    Sort-Object LastWriteTime -Descending | Select-Object -First 1
```

The opt-in native file uses an `mpv-<pid>-<session>.log` name. Search for network errors, HTTP status, TLS/certificate failures, stream open, libavformat diagnostics, and media/protocol selection. **Do not upload raw logs without reviewing and redacting private URLs, query-string tokens and user paths.** The default `player-<pid>.log` is still separate.

Use the *identical* public URL to compare the last accepted M3 executable with the new M4 build, and record DLL SHA-256 and both error codes. A simple HTTPS GET with a byte range can distinguish an inaccessible fixture from mpv-only failures (some servers ignore a range request; inspect HTTP status and content type).

**M4 HTTPS acceptance remains blocked** until the same URL produces decoded video, time/duration values and working pause/seek on real Windows. Existing GitHub-hosted CI does not test external HTTPS stream access.
